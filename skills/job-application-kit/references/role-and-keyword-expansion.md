# Role and keyword expansion, and requirement matching

Job titles are a poor guide. The same work has many names, and good jobs hide behind unexpected titles. Never limit the search or the matching to exact keywords.

## When to run
After the user picks their roles (onboarding question 2), and whenever they add a role. Save the result as `search-terms.md` (private).

## For each chosen role, produce
1. **Title variants** (8 to 15): synonyms, seniority variants, and how different industries name it.
2. **Adjacent roles** the user could credibly do from the same evidence, each with one line of why.
3. **Verticals** where the work is needed (industries or business types).
4. **Skill and tool keywords** drawn only from the user's real background, plus nearby skills they could claim only if true.
5. **Gig-type terms** if the user wants quick or hourly work: task or project work, review and evaluation, labelling or annotation, transcription, moderation, quality assurance, content creation, support shifts, virtual assistance, and similar. Combine them with the role.
6. **Ready-to-use search strings** for job boards (with OR groups and exclusions), and a short "where to set alerts" note. Do not assert which sites are good or pay well unless sourced and current.

Keep it scannable: a compact list per role, not an essay.

## Matching a posting to the user (every job)
1. Extract the posting's **requirements as capabilities** (what the person must be able to do), ignoring the title and buzzwords.
2. For each capability, find the user's **closest real evidence**: a job, project, task, result, training. Include adjacent and transferable evidence.
3. Write the framing in the posting's own language, only where it is true.
4. Mark each as **strong, transferable or gap**. Gaps are not a reason to skip the job. They feed the Improve next list.

## Never
Invent a skill, tool, result or title. Present adjacent experience as direct experience. The aim is the most persuasive honest version of what the user has done.
